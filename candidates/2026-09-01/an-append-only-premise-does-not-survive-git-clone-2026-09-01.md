# A gate that asserts one cause for a failure will misdiagnose every other cause of it

## Body

`secret_scan_gate.py --assume-append-only` reports a baselined finding that no longer matches, and
prints exactly one explanation: *"This content is append-only and was never edited, so this can only
mean the scanner's own pattern got weaker."*

The reasoning is sound and the premise is unchecked. It requires the baselined **file to still be
there**, and the gate never asks.

Root-causing all 11 live regressions on 2026-09-01:

- **3** named files that are **absent from the repository entirely** — `git log --all` returns nothing
  for any of them. `.gitignore` excludes `research/knowledge-home/raw/*.jsonl` **deliberately**,
  because a transcript contains verbatim whatever passed through a session.
- **8** named committed files, each with exactly **one** commit, whose content does not contain the
  pattern in any form. The loosest probes — `AKIA`, `sk-`, `eyJ`, `BEGIN PRIVATE KEY` — return **zero**
  matches. A tightened regex still matches loosely; zero loose matches means the scanned content is not
  the content the baseline was generated from.
- **0** were scanner weakness.

## The structural cause, which generalises

The baseline was generated by scanning the **working tree**. The working tree contains gitignored,
never-committed files. Any other checkout cannot see them, so those entries regress **forever, in every
clone** — and the gate blames the scanner every time.

**ADR-0005's append-only guarantee governs the store on the capture machine. It does not survive
`git clone`.** A gate that inherits an invariant from a document must check that the invariant holds in
the environment it is running in, not assume the document's world.

## The cheap diagnostic that would have caught it

Before concluding a detection regression, ask whether the **loose** form of the pattern still matches.
A regex that was tightened still matches loosely. Zero loose matches means the content changed, moved,
or was never there — never that the pattern got stricter.

## The general rule

An error message that names a single cause is a hypothesis, not a finding. When a check can fail for
several reasons, it must classify which one it hit before it prescribes a fix — otherwise its most
confident output sends the reader to audit the one thing that is working. Both buckets must still fail:
an unperformed check is not a clean check, and "not the scanner's fault" is not "fine."
